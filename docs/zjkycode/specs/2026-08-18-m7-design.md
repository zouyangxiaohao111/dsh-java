## 2. ① 真实 `dsh plugin add` 消费闭环

**链路**:
```
用户跑真实 dsh CLI:
  DSH_HOME=<d> node vendor/dsh/apps/cli/lib/bin.js plugin --profile <name> add <dsh包>
    → pnpm add 装进 $DSH_HOME/profiles/<name>/node_modules
    → reconcile:写 dsh.profile.bundles + cordis.patch.yml 层
然后我们跑:
  DSH_HOME=<d> ./dshj <name>
    → ProfileBoot 解析 $DSH_HOME/profiles/<name>/
    → DshProfileReader 读 bundles → 各 bundle cordis.patch.yml → 组合 entry
    → PluginLoaderService 加载(Java + Node 桥混排)
```

**验证点**:
- 真实 dsh CLI 可跑(vendor/dsh 构建产物 lib/ 已就位);
- 一个新 profile(如 `dsh plugin --profile demo add <小 dsh 包>`)初始化 + 装包;
- `./dshj demo` 经 DshProfileReader 消费 bundles + patch 组合 + 桥加载,HTTP 状态页可见新增包。

**风险**:dsh CLI 在子模块里的可运行性(pnpm workspace 链接、lib/ 完整性);若某个包需额外 seam 加载不了,记录边界(用已验证可跑的包)。

## 3. ② GitHub 源码安装(dshj plugin add java:)

M6-7 PluginInstaller 已解析 `java:<path|github:u/r|git+https://...>`。M7 落地真实 clone:

- 验证用**本地 git repo**(git init 一个小 Java 插件,git clone 走同一路径),公开 URL 通用。
- 与 jar: 安装一致写入 profile 组合配置,可热重载。

## 5. 风险

| 风险 | 对策 |
|---|---|
| dsh CLI 在子模块不可跑 | 检查 lib/ + workspace 链接;必要时用 pnpm dsh 等价入口 |
| 某 dsh 包经桥加载需新 seam | 记录边界,用已验证可跑包做闭环 |
| git clone 网络 | 本地 git repo 走真实 clone 路径,公开 URL 通用 |
| PluginCompiler 编译外部源码需依赖 | 用核心发布后的 provided 依赖,或自包含插件 |
