# dsh-java:里程碑 4 设计 —— 三宿主融合 + 核心对齐

- 日期:2026-08-16
- 状态:已批准(用户审核通过,2026-08-16"开始实现M4")
- 范围:P1 核心对齐(第一工作块)+ 三宿主 PluginRuntimeResolver + NodeWorkerJsHost + 融合证明 spike

## 1. 背景与目标

M1-M3 完成:Java Cordis 核心 + GraalJS 桥 + 热重载(43+ 测试全绿)。M4 达成:

1. **P1 核心对齐**(审计发现的核心缺口):`internal/config`/`internal/update` waterfall 钩子、`internal/*` 事件回填、`Reflect.mixin` 移植——核心是 CLAUDE.md 里"唯一不可替换"的组件,先补齐。
2. **三宿主 PluginRuntimeResolver**:① Java ClassLoader / ② GraalJS / ③ Node worker 动态选,让 ESM/native/重 Node 插件也能直接复用(实测定过 dsh 插件,ESM 依赖是摩擦点)。
3. **NodeWorkerJsHost**:真 Node 跑同一个 ctx shim,转发到我们的 Java 核心(核心永远是我们的 Java cordis,不引入第二个 cordis 世界)。
4. **融合证明 spike**:一个 GraalJS 跑不了的 dsh 插件(ESM 依赖)走 ③ 在 Node worker 跑,ctx 来自 Java 核心。

## 2. 架构

```
Java 核心(dev.dsh.cordis)      ← 唯一不可替换
   ├─ PluginRuntimeResolver(每插件动态选宿主)
   │    ① Java → ClassLoader 宿主(M3 已有)
   │    ② JS → GraalJsHost(进程内,已有)
   │    ③ JS → NodeWorkerJsHost(进程外真 Node,M4 新建)
   └─ JsPluginAdapter(统一,对 PluginModule 抽象,不碰具体宿主)
         ├─ GraalPluginModule(包 GraalJS Value)
         └─ NodePluginModule(包远程函数句柄)
```

### 2.2 NodeWorkerJsHost(真 Node,同 ctx shim)

- Node 进程 + runner 脚本(只 `node:` 内置,无第三方依赖)。
- 通信:stdin/stdout **JSON lines**(NDJSON),hostile-peer 校验(仿 dsh code-runtime-worker-thread)。
- 消息:`load(module)` → `apply(handle, ctxShim, config)` → ctx 桥操作(`on/emit/get/provide/effect`,JS listener 用函数句柄)→ `close`。
- 崩溃/超时 → Java 侧检测 → resolver 兜底。
- **ctx shim**:Node worker 侧 `node-bridge.js` 实现与 `ctx.js` 同一契约面(bridge = RPC proxy,方法发消息过 pipe)。

### 2.3 PluginRuntimeResolver(三宿主)

- 静态检测(加载前,可缓存):Java class? `native`(`.node`/`binding.gyp`)? ESM(`type:module` 无 CJS)? 重 Node(源码扫 `node:stream/crypto/child_process`)?
- 运行时兜底:GraalJS 试跑 → `PolyglotException` 缺模块 → dispose → Node worker 重试。
- 每插件独立选 + 结果缓存。

### 2.4 融合证明 spike

- 一个 GraalJS 跑不了的 dsh 插件(如依赖 schemastery 的,之前要 CJS shim)走 ③ 在 Node worker 跑,ctx 来自 Java 核心,Java 触发它,断言插件行为。

## 4. 风险与对策

| 风险 | 对策 |
|---|---|
| P1 回填波及既有测试 | 语义对齐 fiber.ts/reflect.ts,全量回归 |
| Node 进程管理(启动/崩溃/超时) | 仿 code-runtime:生命周期 + 超时 + 回收;resolver 对瞬时故障重建 worker 重试一次 |

| JS 函数句柄泄漏(长生命周期宿主) | 监听器/effect/disposer 的 Disposable 里 `releaseFn`;worker 侧 fnById 回收 |

### 4.1 NodeWorkerJsHost 同步宿主限制(macrotask / top-level await)

NodeWorkerJsHost 的 runner 主循环是**同步阻塞读 stdin**(`fs.readSync` + 嵌套 `bridgeCall` 共用同一把
读锁),这是进程外 RPC 的正确性前提(嵌套 ctx 调用必须同步等 Java 回复)。代价:事件循环被主循环占住,
`apply`/`invokeFn` 返回的 Promise 只能等待 **microtask 链**(`process._tickCallback()` 泵动),**macrotask
(timer / I/O / TLA 的 `import()` 完成)永远不会同步 settle**。当前实现 `syncWaitPromise` 在等待超过预算后
抛错上报(P3 审计),不做事件驱动重构(需改造为 readline 事件循环 + 双通道桥回复,Windows fd 传递代价高、风险大)。

**失败路径(失败上报,不硬失败)**:
- `load`/`require` 遇 ESM **top-level await** → worker 抛 `ERR_REQUIRE_ASYNC_MODULE` → 归类为明确错误
  "plugin module uses top-level await, unsupported on NodeWorkerJsHost";resolver 的 `loadJs` 转成带可执行
  建议的 `NodeBridgeError` 上报(插件加载失败,fiber 标记 FAILED,host 进程存活)。
- `apply`/`invokeFn` 遇 macrotask await → worker 抛 "macrotask await unsupported";fiber reload 捕获并记
  日志,插件 FAILED,不拖垮 worker。
- resolver 兜底对**瞬时** worker 故障(进程死 / 请求超时 / 管道关闭)重建 worker **重试一次**,再失败明确上报;
  对**确定性**限制(macrotask / TLA)不重试(无益),直接上报。

**规避**:插件避免在 apply / 顶层用 macrotask await;能用 GraalJS 的插件走 ② 宿主;真实 dsh 插件的
`await ctx.loadModule(...)` 等若依赖 TLA,需结构化改造(设计文档记录,不强制实现异步 worker)。
